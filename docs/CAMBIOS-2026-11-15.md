## 2. Reconexión del bot

1. Se verificó que el token anterior respondía `401 Unauthorized` (bot borrado).
2. Se creó un bot nuevo en `@BotFather` y se validó con `getMe` (`@nocodeops_bot`).
3. Se actualizó **solo** `TG_TOKEN` en el env del servicio (31 claves restantes intactas).
4. Se redesplegó y verificó que el contenedor se recreara (`uptimeSeconds` bajo y creciente).
5. El `chat_id` configurado no era el del chat real (`sendMessage` devolvía `chat not found`). Se obtuvo
   el correcto y se fijó en `TG_ALLOWED_CHATS`, `TG_ALLOWED_USERS` y `TG_ADMIN_CHAT`.
6. Se confirmó la entrega con un `sendMessage` de prueba y con el mensaje de arranque del bot.

**Lección:** el `chat_id` de un chat privado es el `user_id` de la persona. Si la cuenta cambió (o el
bot anterior vivía en otra cuenta), la allowlist vieja deja de servir aunque el token sea válido.

## 3. Cambios de código

### `src/telegram.ts`

- Nuevo tipo `TelegramStatus` y estado interno: `pollingSince`, `pollingStopped`, último error de
  polling, último envío OK/error y contador de fallos consecutivos.
- `markPollingStarted()`: lo llama el `onStart` de grammY.
- `markPollingError(message)`: lo llama el `.catch` de `bot.start()` y el handler de rechazos.
- `status()`: snapshot serializable para `/health`.
- `healthy(startGraceMs = 300 000)`: `true` si Telegram no está configurado (modo consola) o si está
  entregando. Mientras el polling no haya arrancado no alerta hasta pasados 5 minutos: el primer ciclo
  del watcher corre antes de `bot.start()` y puede tardar.
- `describeProblem()`: motivo legible para el detalle del incidente.
- `send()`: al éxito resetea fallos; al error incrementa el contador y guarda el mensaje.

### `src/index.ts`

- En cada ciclo, si `notifier.healthy()` es falso se agrega el hallazgo:
  ```ts
  { key: 'ops:telegram', severity: 'critica', title: 'Bot de Telegram sin entregar', detail: … }
  ```
  El motor de incidentes lo abre una vez y lo cierra cuando Telegram vuelve.
- Se pasa `telegramStatus: () => notifier.status()` a `startHttp`.
- `BOT_COMMANDS` + `bot.api.setMyCommands(BOT_COMMANDS)` al arrancar (con `.catch` para no romper).
- `bot.start(...)` ahora captura el rechazo:
  ```ts
  bot.start({ …, onStart: () => { notifier.markPollingStarted(); … } })
    .catch((err) => notifier.markPollingError(err.message));
  ```
- Handlers de proceso: `unhandledRejection` (loguea y marca polling caído si aplica) y
  `uncaughtException` (loguea). `main().catch(...)`.

### `src/http.ts`

- `HttpDeps.telegramStatus?: () => unknown`.
- `GET /health` agrega `telegramStatus` (o `null`).

### `package.json`

- Versión `0.8.0`.
- `"test": "node --import tsx --test test/rules.test.ts test/incidents.test.ts test/time.test.ts"`.
- `"check": "npm run typecheck && npm test"`.

### `.github/workflows/ci.yml`

- Se agrega `npm test` entre `typecheck` y `build`.

### Tests nuevos

| Archivo | Cubre |

## 7. Rollback

- **Código**: `git revert` del commit de 0.8.0, o desplegar el commit anterior de `origin/main`.
- **Env**: reaplicar el env anterior con `updateAppEnv` (se conserva el que se leyó antes de cambiar) y
  redesplegar.
- **Bot**: si el token nuevo fallara, crear otro en `@BotFather` y actualizar `TG_TOKEN`; la allowlist
  no depende del bot.
- **Datos**: `/data/state.sqlite` se puede perder sin drama (se reconstruye); el histórico está en
  Postgres.

## 8. Riesgos y notas

- `uncaughtException` se loguea **sin** terminar el proceso para evitar crash loops. Es una decisión
  deliberada: un estado corrupto podría persistir hasta el próximo deploy. Si se prefiere el
  comportamiento clásico (salir), cambiarlo y documentarlo.
- `setMyCommands` lista los comandos de ambas líneas (`/diag`, `/sesiones`, `/servidor`, etc.), que ya
  existen en el árbol integrado.
- `/health` y `/metrics` siguen sin autenticación y publicados en `18080`.
